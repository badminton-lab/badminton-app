# 設計メモ

バドミントン指導者向けの、練習メニュー集サイト。Next.js 16（App Router）・React 19・Tailwind 4。データベースなし。内容はすべて `src/data` にある。
最終更新：2026年10月。

## 公開の仕組み（重要）
- 公開サイトに出るメニューは、`reviewed: true`（運営者確認済み）のものだけ。0件のときは、ホームに「準備中」を出す。
- 開発中は、`NEXT_PUBLIC_SHOW_UNREVIEWED=1 npm run dev` で、確認前のメニューも表示できる（本番では無効）。メニュー詳細は、開発中なら確認前でも開ける。
- 編集は、ローカルの開発サーバーだけで行う（`/editor`、`/editor/content`）。本番には、編集ページも保存APIもない（404）。
- **保存しただけでは、公開されない**。編集画面の「公開する」ボタンが、データ2ファイル（`overrides.json`・`content.json`）だけをコミットしてプッシュする。ホスティングが、プッシュで自動デプロイする設定にする（未設定）。

## データの層（メニュー）
`menus/*.ts`（`defineMenus` で区分ごとに作成）→ `enrichments.ts`（ねらい・手順などの深掘りを合成）→ `illustrations.ts`（コート図のないメニューにイメージ図を付ける）→ `rawDrills` → `applyOverrides`（`overrides.json` の差分。`null` は削除）→ `allDrills` → 公開用 `drills`（確認済みのみ）。

- メニューの id（`d01`、`hf01` など）は、お気に入り・プランの保存に使う。変更・並べ替えをしない。追加は、各ファイルの末尾に。
- 区分は、パターン練習／ドリル（複数人が順に回るローテーション型）／手投げノック／ラケットノック／フットワーク／アップ／ストレッチ／運動遊び。
- 種目（`courtType`）は、シングルス／ダブルス／どちらでも／共通（アップ等）。トップの絞り込みに「種目」がある。シングルスを選ぶと「シングルス＋どちらでも＋共通」、ダブルスを選ぶと「ダブルス＋どちらでも＋共通」が出る（URLは `t=singles|doubles`）。
- 追加メニューのファイルと id：ダブルス用 手投げ `hd01–30`（`handFeedDoubles.ts`）、ラケット `rd01–30`、パターン `pd01–30`、フットワーク `fd01–30`。股関節（可動域・動き出し）のアップ `wh01–18`、ストレッチ `sh01–12`（どちらも `hipMobility.ts`。図は `illustrations.ts` の `wh**`・`sh**`、ポーズは `poses.ts` の股関節まわり）。ダブルス図の補助は `dsl.ts` の `knockPair`・`pairMoves`・`TOP_BACK`・`SIDE_SIDE`。
- 区分ごとの件数をそろえるための追加（2026年10月14日）：ドリル `dr23–50`（28件。`drill.ts` の末尾）、運動遊び `pl30–45`（16件。`play.ts` の末尾。図なし）、ストレッチ `st33–38`（6件。`stretch.ts` の末尾。図なし）。課題タグも `drillTags.ts` に付けた。これで、ドリル50・ストレッチ50・運動遊び48件。ほかの区分（パターン練習77・フットワーク65・手投げノック64・ラケットノック60・アップ56）は、すでに50件を超えているので、増やしていない。
- これらはすべて「確認前」。運営者が `/editor` で確認して、「運営者確認済み」にするまで公開されない。

## 課題タグ（逆引き）
- タグの一覧と分け方は `src/data/tags.ts`（候補は運営者の確認待ち）。メニューへの付与は `src/data/drillTags.ts`（id → タグ）か、`/editor` の「課題タグ」チェック。
- 一覧ページの「条件」に「課題から探す」が出る。複数のタグを選べて、選んだすべてに当てはまるメニューだけ残す（URL は `?g=タグid,タグid`）。メニューが1件もないタグは出さない。キーワード検索にもタグ名が効く。詳細ページには、タグが `# 打力強化` の形で出て、押すと同じタグの一覧へ飛ぶ。
- 運営者が決めたこと（2026年10月14日）：タグ名は短くする（意図が伝わらないものは外す）。「配球」「連係」（「連携」でも誤りではないが、スポーツの動きのつながりには「連係」を使い、既存のメニュー名にも合わせた）「奥（後ろ）」「実戦形式」とする。「運動遊び」は区分と同じなのでタグにしない。複数タグはAND検索。付与の対象は公開前を含む全メニュー。
- 区分（パターン練習・アップなど）とは別の軸。1つのメニューに複数付けてよい。

## 図
- **コート図**（`CourtDiagram`）：座標は0〜1。縦向き表示。フィーダー（ノッカー）がいれば下、いなければ練習者が下。矢印には順番号。番号が重なったときは、エディタで番号（黒い丸）をドラッグして動かせる（矢印の中ほどからのずれを `orderShift` に保存。向きが変わっても同じ方向へずれる。選んだ矢印の「番号の位置を戻す」で元に戻る）。
- **場面図**（`SceneView`、`scenes.ts`、エディタは `SceneEditor`）：上から見た図。運動遊び・陣取り・リレーなど向き。320×200の座標、コートの線は x16〜304・y22〜182。人は**色つきの丸のコマ**（中に番号・役名、向きの印は任意）。部品は、コマ・エリア（半透明の面）・ライン・矢印（実線=人の動き、破線=物の動き）・文字・吹き出し・道具アイコン（しっぽ・風船・ラケット・シャトル・ボール・コーン・フープ・宝・旗・カゴ）。床は木の色（無地も選べる）。
- 図の種類は、メニューごとに、コート図／人の体／場面図／図なしから1つ選ぶ（編集画面の「図の種類」）。表示の優先順位は、コート図 → 場面図 → 人の体。
- **イメージ図（人の体）**（`IllustrationView`、型は `types.ts`）：320×200の座標。部品を重ねて描く（人・ラケット・シャトル・ボール・コーン・的・矢印・線・四角・文字）。
  - 人は、ちびキャラ（骨組みは `src/lib/figure.ts`、描き方は `IllustrationView.tsx`）。見た目・色・ペアの図の決まりは `docs/ILLUSTRATION_RULES.md`。全図の一覧は、開発サーバーの `/editor/figures`。骨組みは、棒人形のとおり、角度は絶対角度（0=下、90=右、180=上）。腕は[上腕, 前腕]、脚は[太もも, すね]。R=手前、L=奥。`groundedY` で足を床に合わせる。
  - ポーズのひな型は `poses.ts`。体は、シャツ＝人の色、短パン＝その濃い色、肌・髪・くつは共通（髪は short / ponytail）。手を相手に合わせる `reach()`（`illustrations.ts`）で、ペアの図を作る。
  - 初期の図は `illustrations.ts` に、部品を組み合わせて書いてある。エディタで、メニューごとに直せる（`overrides.json` に保存）。
  - コート図とイメージ図の両方があるメニューでは、コート図だけを表示する。

## メニュー以外の内容
- `rules.ts`・`trivia.ts`・`gear.ts`・`products.ts`・`site.ts` が元データ。エディタで保存すると、`content.json` に**一覧がまるごと**保存され、元データの代わりに使われる（保存後は、元のファイルを直しても反映されない）。「元の内容に戻す」で、保存した内容を消せる。
- 項目の定義と検証は `contentSchema.ts`（エディタと保存APIで共用）。

## クイズ
- 元データは `quiz.ts`（51問。○×と3択、区分5つ、対象は「小学生から／中学生向け」）。エディタ（`/editor/content`）の「クイズ」で、追加・編集できる（`content.json` にまるごと保存）。
- 選択肢は「正解を1行目」に書く。○×は「○」「×」の2行、3択は2〜4行。画面では、3択は問題の id から決まる順に並べ替える。
- 各問題に、出典（リンク）・確認時期・ファクトチェックの記録（`factCheck`、公開されない）を持たせる。確認の記録は `docs/QUIZ_FACTCHECK.md`。
- 点数方式（21点制→15点制）、メダル数、記録は変わるので、問題文や解説に時期を入れ、確認時期を残す。

## 練習プラン例
- 元データは `samplePlans.ts`（コード上のみ。エディタでは編集できない）。各プランは、段階（準備運動・ノックなど）ごとに、メニューの id と時間を並べる。合計時間は自動で計算。
- 公開サイトでは、確認済みのメニューだけがリンクになり、ほかは名前だけ（「詳細は準備中」）。「この例を『今日のプラン』に入れる」で、確認済みのメニューだけを、`/plan` のプランに入れる。
- メニューを入れ替えるときは、id が存在すること・合計時間が合うことを確かめる。

## セキュリティ（2026年10月14日に点検）
- **データベースがない**ので、SQLインジェクションは起こらない。利用者が入力した文字を、命令として実行する処理（`eval`・`exec` など）も、公開側にはない。`dangerouslySetInnerHTML` は、テーマ切り替えの固定の文と、構造化データ（JSON-LD。`<` を無害な文字に置き換えて出力）だけ。画面に出す文字は、Reactが自動で無害化する。
- 利用者の入力は、検索語・絞り込み（URLの条件）・お気に入り／プラン（ブラウザ内の保存）だけ。保存の読み込みは、型を確かめてから使っている。外部リンクは `rel="noopener noreferrer"`。リンク先に使えるのは `https://`（とメールの `mailto:`）だけ（`contentSchema.ts`）。
- 応答ヘッダー（`next.config.ts`）：`X-Content-Type-Options`・`X-Frame-Options`（ほかのサイトの枠に埋め込ませない）・`Referrer-Policy`・`Permissions-Policy`・`Strict-Transport-Security`・`X-Powered-By` の非表示。**CSP（読み込みを許す場所の制限）は本番だけ**。Googleフォーム以外の送信先（Formspree 以外）を「お問い合わせフォームの送信先URL」に使うときは、`next.config.ts` の `connect-src` も直す。
- 開発用の編集API（`/api/dev/*`）：本番では常に404。開発中も、`src/lib/devGuard.ts` で、宛先が localhost のとき・送信元が同じ場所のとき・JSONで送られたときだけ受け付ける（同じネットワークの他の端末や、開いている別のサイトから、保存・公開（git push）を実行されないため）。**開発サーバーは、同じネットワークからも見える状態で起動する**ので、画面（`/editor`）自体は他の端末からも開けるが、保存・公開はできない。
- 依存パッケージ：`npm audit --omit=dev`（公開サイトに入るもの）は、問題なし。開発用の道具（eslint まわり）に、重大度「高」の指摘が5件ある（`braces` の、深く入れ子にした指定でフリーズする問題）。公開サイトには入らず、直すには古い版に戻す必要があるので、そのままにしている。
- 運営者の作業：ホスティングを決めたら、HTTPSが有効なことと、環境変数（`NEXT_PUBLIC_SITE_URL`）を確認する。広告・アクセス解析などの外部スクリプトを入れるときは、CSP（`script-src`・`connect-src`）も直す。
